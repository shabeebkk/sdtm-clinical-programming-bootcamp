## Why XPT v5, a format from the 1980s?

Because it is **open, documented, and readable without SAS**. A regulator must be able to open
your data in thirty years without buying a licence. That is a good reason, and it is why the
format's age is tolerated.

The cost is a set of hard limits — and those limits **retroactively explain SDTM conventions you
have already followed and probably found arbitrary**:

| XPT v5 limit | The SDTM convention it explains |
|---|---|
| dataset name ≤ **8** chars | domains are 2-letter codes (`DM`, `AE`), `SUPPAE` is 6 |
| variable name ≤ **8** chars | `AESTDTC`, not `ADVERSE_EVENT_START_DATE`; `--TESTCD` is capped at 8 |
| label ≤ **40** chars | why labels read terse |
| character length ≤ **200** bytes | why `--ORRES` is not a free-text essay field |
| ASCII only | why CT values carry no accents |

So `VSTESTCD` is 8 characters not because CDISC prefers brevity, but because **the transport
format cannot carry more**.

## Section 1 — Check *before* you export

The XPORT engine does **not** stop you breaking its own rules. It truncates quietly, exactly
like everything else in SAS. So the notebook checks first, reading `DICTIONARY.COLUMNS` —
SAS's own catalogue of every variable in every library, which is worth knowing well beyond
today.

```sas
select ... from dictionary.columns where libname = "SDTM" having issue ne "";
```

ABC-01 passes with zero issues. **That is not luck** — it is the naming conventions doing their
job (Exercise 1).

## Section 2 — Export

```sas
libname xptout xport "&outpath/dm.xpt";
proc copy in = sdtm out = xptout;  select dm;  run;
libname xptout clear;      /* releases and finalises the file */
```

**One file per dataset** — `dm.xpt`, `ae.xpt`, … — which is the FDA convention, not one big
file. Note the `clear`: the file is not finished until the libref is released.

## Section 3 — Prove the round trip

An `.xpt` you cannot read back is worthless, so each file is read again and its row count
compared to the source. This is the **minimum** honest check — see Exercise 6 for what it still
misses.

## define.xml — and why it is *generated*

Open `data/define/define.xml`. The important thing is not the XML; it is that **nobody typed
it**. It is generated by `data/build_define_xml.py` from the same mapping specification the
programmers map from.

That is the whole point of holding metadata as **data**: one source, two consumers — the
programmers and the define. Change the spec, regenerate, and the define follows. If they ever
disagree, the spec wins.

What it carries, per variable: name, label, type, **length**, **origin** (collected on the CRF?
assigned? derived?), any **codelist**, and for derived variables a **method** describing how.

```xml
<ItemDef OID="IT.DM.USUBJID" Name="USUBJID" DataType="text" Length="13">
  <Description><TranslatedText xml:lang="en">Unique Subject Identifier</TranslatedText></Description>
  <def:Origin Type="Derived"/>
</ItemDef>
```

`Length="13"` was read from the **actual data** (`ABC-01-01-001` is 13 characters), not guessed
— see Exercise 3.

> ⚠️ **Honest scope.** This define.xml is structurally correct and well-formed, and the
> generator self-checks that every dataset, variable and method made it in and that no method is
> left orphaned. It is **not** schema-validated against `define2-0-0.xsd` — that needs Pinnacle
> 21, which is what a real submission would use. Treat it as a faithful teaching artifact.
